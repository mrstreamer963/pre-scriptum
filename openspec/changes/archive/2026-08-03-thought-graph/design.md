## Context

См. proposal.md — Why. Текущее состояние: пустой репозиторий, нет существующего кода. Проект — новое локальное SPA-приложение (TypeScript) с переносимым core. Ключевые ограничения: всё работает в браузере без сервера, приватно и оффлайн; core должен быть переносимым на Node.js позже без переписывания домена.

## Goals / Non-Goals

**Goals:**
- Чистая гексагональная архитектура: core (домен) отделён от адаптеров окружения через порты.
- 2D-граф с плекс-навигацией, рендер в браузере.
- Подсвеченная семантическая сеть: мягкие связи не меняют ручную раскладку.
- Данные в IndexedDB, эмбеддинги локально через transformers.js.

**Non-Goals:**
- Синхронизация и multi-user (локально, один пользователь).
- Авто-раскладка графа по семантике (организующая семантика) — вне PoC.
- Node.js-серверная реализация сейчас — только проектирование core под неё.
- Полноценный редактор документов — базовый markdown-редактор достаточен.

## Decisions

### D1: Гексагональная архитектура (порты и адаптеры)
Core — чистый домен без зависимостей от окружения. Взаимодействие через порты:
- `StoragePort` — CRUD карточек, связей, документов, эмбеддингов.
- `EmbeddingPort` — генерация эмбеддинга из текста.
- `SearchPort` — векторный поиск по косинусной близости.

Адаптеры браузера: `IndexedDBStorage`, `TransformersEmbedding`, `CosineSearch`. Позже — Node-адаптеры (файлы + SQLite, onnxruntime-node, HTTP API) без изменения домена.

**Альтернативы:** монолит без разделения — проще, но не переносим; сервис-ориентированный — избыточно для локального SPA.

### D2: Модель данных
- **Карточка**: `{ id, title, body, createdAt, updatedAt }`.
- **Связь**: `{ id, from, to, type: 'parent' | 'reference' }` — направленная.
- **Документ**: `{ id, title, content, createdAt, updatedAt }` — отдельная сущность, не узел графа.
- **Эмбеддинг**: `{ cardId, vector: number[] }` — кэш, пересчитывается при изменении карточки.

Связи хранятся как отдельные сущности (не вложенные в карточки) — это упрощает графовые операции (плекс, поиск соседей) и перенос на SQLite.

**Альтернативы:** связи вложены в карточки (wiki-links) — проще для файлов, но усложняет графовые запросы и перенос на граф-базу.

### D3: Плекс-навигация
Плекс — радиальное облако прямых связей текущей карточки. Рендер: текущая карточка в центре, прямые связи по кругу. Перескок меняет текущую карточку и перестраивает плекс. Раскладка плекса — ручная/фиксированная (углы по кругу), не семантическая.

**Альтернативы:** свободный холст (Miro-стиль) — отклонён, т.к. не решает масштабируемость и не даёт TheBrain-ощущения; force-directed авто-раскладка — отклонена для жёстких связей (нестабильна), оставлена только для мягких.

### D4: Подсвеченная семантика
Мягкие связи вычисляются на лету: для текущей карточки ищем топ-K семантически близких карточек без жёсткой связи, отображаем серым пунктиром. Не меняет раскладку. Порог близости настраивается. Предложение жёсткой связи — UI-действие поверх мягкой.

**Альтернативы:** организующая семантика (авто-раскладка по векторам) — отклонена, вне PoC, нестабильна при пересчёте.

### D5: Тех-стек UI для 2D-графа
Канвас-рендер с библиотекой графов. Кандидаты: `react-flow` (зрелый, но тяжёлый для плекса), `cytoscape.js` (мощный граф, хорош для плекса), свой рендер на canvas (максимум контроля, больше работы). Для PoC — `cytoscape.js` как баланс возможностей и скорости.

**Альтернативы:** SVG — проще, но медленнее на больших графах; WebGL — избыточно для PoC.

### D6: Эмбеддинги в браузере
`transformers.js` (WASM/WebGPU) с лёгкой embed-моделью (например, all-MiniLM-подобная). Модель загружается локально, данные не покидают машину. Векторный поиск — линейный скан по косинусу (для PoC достаточно; при росте — HNSW/индекс).

**Альтернативы:** серверные эмбеддинги — отклонены (нарушает локальность/приватность); WebNN — рано, поддержка незрелая.

## Risks / Trade-offs

- [Размер модели эмбеддингов в браузере] → Mitigation: лёгкая модель, ленивая загрузка, кэш в IndexedDB.
- [Производительность векторного поиска при росте карточек] → Mitigation: линейный скан для PoC, при росте — индекс (HNSW) за портом `SearchPort`.
- [Нестабильность мягких связей при пересчёте эмбеддингов] → Mitigation: мягкие связи вычисляются на лету, не сохраняются, не влияют на раскладку.
- [cytoscape.js как зависимость] → Mitigation: изолировать рендер за портом UI, при необходимости заменить.
- [Переносимость core на Node] → Mitigation: строгие порты, домен без импортов окружения, тесты на домене с фейковыми адаптерами.

## Migration Plan

Новый проект, миграции нет. Данные в IndexedDB — схема версионируется (IndexedDB version). При будущем выносе на Node — экспорт/импорт данных через порт хранилища.

## Open Questions

- Точная embed-модель и её размер — решается на этапе реализации, не влияет на specs/архитектуру.
- Порог семантической близости для мягких связей — настраиваемый параметр, уточняется на PoC.
- Библиотека графов (cytoscape vs react-flow) — финальный выбор на этапе реализации, изолирован за портом UI.
